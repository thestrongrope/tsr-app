# Testing and the local stacks

How to run every check, and the rules of each stack. The short list of commands is in the root `CLAUDE.md`; this page has the detail.
What was last measured is in `docs/status.md`.

## The stacks

| Stack | What it holds | Rule |
|---|---|---|
| dev (`docker-compose.dev.yml`, `https://gateway.tsr-app-dev.orb.local`, an OrbStack name) | may hold REAL member data and device tokens | no contract script, seed or reset; never a sending worker (`push-drain`, `class-schedules`) |
| test (`tools/test-stack.sh`, project `tsr-app-test`, gateway :8089) | synthetic data only | the only kind of stack Hurl may run against |
| lane n (`TSR_STACK=n`, 1 to 8, gateway `8100+n`) | synthetic data, one per parallel worktree | built from the checkout its script is in |
| parity (`tools/parity-php/`, PHP on 127.0.0.1:18091) | the PHP reference on synthetic data | one shared stack; `parity` runs take a lock |

Never run `docker-compose.yml` (production) locally.

Required settings (the API does not start without them): `TSR_DB`, `TSR_FIREBASE_PROJECT_ID`, and `TSR_GOTENBERG_URL` (the Gotenberg container that renders PDF report downloads; the compose file sets it; production must too).

## Running every Hurl file, and the lane scripts

The test lanes' routes have their own contract scripts, `tools/contract-<lane>.sh test|parity [--prepare]` (lanes: deletion, edge, grants, notify, quizwrites, reports2, sheets); each loads only its own fixtures and mints tokens into `build/test/<lane>.vars`. To run EVERY Hurl file on the test stack: run the identity, membership, classes and assessment prepares, then each lane's `test --prepare`, then the all-files command above with one `--variables-file` per file in `build/test/*.vars`, leaving out files named `*-php-only.hurl` (they pin what only PHP does). Measured on 12 Nov 2026 (after the owner's decisions were built): 235 files, 3119 requests on the new API (latest full run, with Elasticsearch on the test stack, the guide routes, permissions version 5 and the calendar: 244 files, 3246 requests, run the calendar lane's `--prepare` too; with the six Library files, last run 14 Nov 2026: 250 files, 3344 requests); 1342 database tests (13 Nov 2026). The six `domains/content/spec/tests/v1-*.hurl` files pass only where the `content-refresh` worker has loaded `db/synthetic/content`: the default test stack runs it, a lane must be started with `TSR_LANE_WORKERS=content-refresh`. Do not run one lane's contract script alone between two full runs unless you re-run every prepare afterwards: a bulk add hands out the next free token, and fixtures that reset by token range must not catch such a member (the edge fixture did; it now resets only its own tokens). After a `git merge` or checkout rewrites `hosts/gateway/default.conf`, restart the stack's gateway container: its single-file mount goes stale and nginx keeps the old configuration.

## Background workers on the stacks

**Background workers (12 Nov 2026).** The API image has a second run mode, `--workers` (`hosts/api/WorkerMode.cs`; the loop is `shared/api/PeriodicWorker.cs`): it serves only `/health` and runs the workers named in `TSR_WORKERS` (comma separated; an unknown name refuses to start; empty runs none). The normal API mode never runs a worker. Built: `push-drain` (notifications: sends `platform.outbound_messages` through FCM, a tick a minute that takes batches of 50 rows for up to 50 seconds), `class-schedules` (notifications: fires due scheduled class notifications by queueing pushes), `search-feed` (search: rebuilds the Elasticsearch index from the published views every 10 minutes), `content-refresh` (content: copies the published content files of `TSR_CONTENT_DIR` into content's Library tables, at start and every 5 minutes; it sends nothing outward, so it is safe on a lane: `TSR_LANE_WORKERS=content-refresh`; `db/tests/ContentRefreshTests.cs`). Production runs no timer: the one-off job `content-load` (`--load-content`, `ContentModule.LoadContentAsync`; `db/tests/ContentLoadTests.cs`) runs one tick at each deploy over the content baked into the image. One tick each is what the database tests call (`db/tests/TestPushDrainTests.cs`, `TestClassScheduleWorkerTests.cs`, `TestSearchFeedTests.cs`). `docker-compose.dev.yml` has an `elasticsearch` service (the image production runs) and a `workers` service behind the compose profile `workers`: a plain `up` of the dev stack starts neither, and `TSR_WORKERS` is empty unless set. **Never name a sending worker (`push-drain`, `class-schedules`) on the dev stack: its database holds real device tokens, so with FCM credentials it would push to real phones.** The default test stack turns the profile on with `search-feed` and `content-refresh` only (`docker-compose.test.yml`), so its `GET /search` answers from a real index; a lane stack (`TSR_STACK=n`) has no Elasticsearch unless it is started with `TSR_LANE_WORKERS=search-feed`, which gives it its own (no host port) and that worker only; the persona Patrol lane uses it. Production (Dokploy, `docker-compose.yml`) is not wired in this repo yet. One worker instance is the supported setup. Not built: the WhatsApp reminder runner (the Node notifier still uses the old MariaDB). The search feed and `GET /search` are proven against a real Elasticsearch 9.2.3 on the test stack (`search-new-api.hurl`); FCM is unverified. Details: the `CLAUDE.md` of platform, notifications and search.

## When the PHP reference moves

Archive tsr-account `develop` into a fresh `build/parity-php/src/` (keep the old copy beside it; steps in `tools/parity-php/README.md`), rebuild the parity `api`
container, run every `parity` script, and diff `web/api/mobile/index.php` for new routes. What was ported at each move is in `docs/status.md`.
