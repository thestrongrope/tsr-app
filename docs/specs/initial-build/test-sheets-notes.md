## Findings

- **8 (subset search): settled, fixed.** PHP runs the same 2^n loop with no cap (`quizadmin.php:1443-1491`; its comment calls 128 iterations the worst case). The new code decided it with the same loop capped at 20 started episodes, about 3 seconds for 20 feasible days on this machine, on every `GET /admin/quiz` (test first: `QuizCrossDay.Tests.cs`, three red tests). Now a matching decides (each started episode needs `Needed` distinct candidates; a candidate serves one episode): the verdict equals Hall's condition over subsets. A failure is named as before: up to 12 started episodes by PHP's own search (first failing subset in mask order, so the reason text is PHP's, proven equal to the old loop on 400 random quizzes), above that by the episodes the matching could not serve. 30 episodes with a shortage now take milliseconds, and more than 20 started episodes are no longer refused. Not cached per download: PHP recomputes on every read and member data changes between reads. Negative winner counts: the matching treats them as 0 where PHP's sum would subtract; the draw refuses negative counts anyway (409).
- **12 (SHA-256 against SHA-1): settled, no change.** PHP (`OutboundMessagesModel::dedupeKeyFor`): `substr(key, 0, 150) . ':' . sha1(recipient)`; here: first 150 characters, `:`, first 20 bytes of SHA-256 in hex (both 40 hex characters, 191 at most; the unique index is `(channel, dedupe_key)`). A cut-over needs: (1) a quiz PHP already announced must not be switched off and on again on the new API, or each device gets a second push (a new key does not match PHP's queued row); (2) or let PHP's worker drain its queue first, or re-key the unsent `quiz-announce:` rows once with the new formula; (3) PHP cuts at 150 bytes, here 150 characters, so a title with non-ASCII text near the cut differs. The inbox copy is found by its text, so it is not affected.
- **13 (force_quiz_mode, +05:30, limits): settled, decisions needed.** `force_quiz_mode`: `get_settings()` (functions.php:511-537) copies only host, database, username, password, timeoffset, quiz_settings_google_sheet_id, redirectUri and report_api_key from the environment; `force_quiz_mode` could only come from a deployment-defined `get_local_settings()` (functions.php:69-83, "Local dev may define this in a file"). Nothing in this repo or the parity compose sets it, so it is not observable here and not ported. Decision: confirm production does not define it; if it does, it is one line in `QuizAdmin.SettingsAsync`. Timestamps: PHP shifts by env `TIME_OFFSET` (parity: `PT5H30M`; code default `PT0H0M`) and only when set; here a fixed +05:30. Same on parity; decision: confirm production's `TIME_OFFSET` is IST. Limits PHP lacks (30 episodes, 20 ids, winner counts negative or above 10000): all stricter than PHP, tested (`standard-mcq-update-new-api.hurl`, `The_limits_PHP_lacks...`), listed for the owner; none changed. A `today_override` that is not a date is ignored here (PHP: 500), tested.
