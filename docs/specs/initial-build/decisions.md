# Owner decisions on the initial build (Asif, 12 Nov 2026)

The table below is the list as collected on 12 Nov 2026 from the test notes, `build-out-findings.md` and the four `review-*.md` files. It describes what happened THEN; this section says what was decided. Numbers are the table's.

## Decided and built (on `dotnet-11`, proven by database tests and the Hurl suite)

| # | Decision | Where |
|---|---|---|
| 1 | A completion deletes the Firebase account of every user row of the token (at most 20 rows), before the database | `domains/identity/CLAUDE.md` |
| 2 (part) | A Firebase delete found by an email, or returning a uid, that another member's row holds is refused with 409 | `domains/identity/CLAUDE.md` |

| 22 (part) | A GENDER announcement uses one audience for the push and the inbox; the other audience differences stay as PHP | `domains/notifications/CLAUDE.md` |

Also built from the reviews, not in the table: the gateway gives the three synchronous push routes 130 s; search re-reads a guide before showing it; a push is no longer cut short or left unrecorded when the caller goes away.

## Decided: keep as PHP for now

- 2 (the rest): the operator does not confirm the Firebase account found by email. The route takes no body and the admin app in tsr-account calls it, so a mandatory confirmation would break the store-live build. Revisit when the admin app next changes (proposal: an additive preview route and an optional confirmation body).
- 7: one holder of `deletion-requests:manage` can raise, confirm and complete a deletion alone.
- 34: rate limits are in memory per process. Move them to the database before a second API instance runs.
- Every other row of the table (3, 5, 9 to 18, 21, 23 to 33, 35): unchanged. Where the Options column names a "keep" option, that is the one in force; 3 keeps the stricter new behaviour it describes.
