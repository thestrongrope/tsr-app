# tsr-app organization plan (draft, 2026-11-08; brought in line with the stack decision 2026-11-10)

How `tsr-app`, TSR's public monorepo, is designed and organized. Part 1 is the high-level summary
of how we are designing the app. Part 2 is the current mid-level view: folders, how a domain is
built, and what sits around the domains. Working draft, edited live; reviewed 2026-11-08
(`repo-structure-review.md`). Numbers in `[ ]` are the software units of
`software-data-split.md`. Out of scope for now: the other TSR tools (creative, hadith,
translation, planner and the rest) and the private data repo.

**Stack.** Language, database and libraries are decided in `dotnet-stack.md` (2026-11-09): C# on
.NET 10, PostgreSQL, EF Core or Npgsql per domain, NUnit, Hurl contract tests. This document owns
the layout and the rules; where the two differ, `dotnet-stack.md` wins on technology. **The sample
in this repo predates that decision**: it runs on MariaDB with MySqlConnector, `.sql` migrations,
xUnit and C# contract tests, to mirror the PHP route. It proves the layout, not the stack.

**When this layout applies.** The 2026-11-28 flip publishes today's layout unchanged, and prod
keeps deploying from the old private repo (option (a), `plan.md`). This layout is the target for
tsr-app after the deploy source moves to it (task L1). Each folder move lands together with the
production change it needs (Dockerfiles, entrypoint, compose, Codemagic, Dokploy watch paths),
agreed first. New folders that touch no production path (`domains/*` for new slices, `hosts/api`,
`hosts/gateway`) can start earlier.

## Part 1: How we are designing the app

### What we are building

One product with two delivery paths and one API. The Flutter app serves everything behind sign-in
on every device. The public site is static or pre-rendered HTML, so it is indexable, shareable and
searchable. Both read the same data through the same API: the app at runtime, the site at build
time and for search.

```
 Flutter app                                         Public site
 (phone, tablet, desktop, web; XR as a window)       (static HTML, built from the API)
        │                                                   │
        └──────────────────► api. ── gateway ◄──────────────┘
                                       │
                     ┌─────────────────┴──────────────────┐
              new API: one module per domain          legacy PHP
              (vertical slices inside)                (shrinks slice by slice)
                     │
       PostgreSQL (system of record; MariaDB until the move) · Elasticsearch (search) · Redis Streams (events, via outbox)
       scheduler and workers (push, WhatsApp, search indexer) consume the stream
```

### How it is designed

1. **Domain-first.** Each bounded context is one folder holding its whole stack: a
   language-neutral spec, one API implementation and the app screens. A typical change touches
   one domain folder.
2. **One API, one database.** All domain modules run in one API process (a modular monolith). One
   PostgreSQL database holds every table, one schema per domain (MariaDB until the move, which
   comes before the new API: `dotnet-stack.md`). Each table is owned by one domain, except a few
   named platform tables (Part 2, section 3.3).
3. **Vertical slices inside a domain.** One folder per use case (a command or a query), holding
   everything it needs. CQRS-lite falls out of this.
4. **Dependencies point inward, to the domain.** The domain knows nothing about the database, the
   API or Firebase. Infrastructure implements ports at external boundaries.
5. **Clients are presentation.** The Flutter app and the site hold no business rules (`CLAUDE.md`:
   rules live in models, not in screens).
6. **Hosts compose, they do not decide.** What ships (the API process, the app) wires domains
   together and holds no rules. Programs with their own logic (site generator, calendar feed)
   are named as such (Part 2, section 3.1).
7. **Shared stays small.** Only technical plumbing every domain needs, never a rule. Who is
   calling is `identity` (AuthN); what they may do is `access` (AuthZ), the one domain every
   other domain may depend on.
8. **Deployable per domain when needed.** Any domain's API can run in its own host and scale on its
   own, without moving code (Part 2, section 3.2). Start with one host for all domains: ready,
   not yet.

Lightweight DDD per `CODING-GUIDELINES.md`: ubiquitous language, module boundaries, value objects;
full tactical DDD only where a domain's complexity earns it. The layout follows the common
modular-monolith with vertical slices pattern (checked online 2026-11-08).

### How it evolves

Mapped to `target-architecture/plan.md`:

1. **Stage 0, clean seams (mostly done):** no SQL in PHP pages, no role lists outside
   `PermissionsModel`.
2. **Stage 1, outbox and Redis Streams** inside the current PHP stack.
3. **Stage 2, first slice:** `POST /feedback` built as a slice in `domains/platform`, passing the
   same contract tests as the PHP route. The gateway is introduced here, routing that one path.
4. **Stage 3, slice by slice:** each use case moves the same way, and PHP shrinks until it is gone.
   Cron jobs move into the scheduler as their handlers move.
5. **Afterwards, only under pressure:** a domain that needs its own deploy or scaling gets its own
   host and a gateway line. No code moves.

### What it is not

- Not microservices now: one API process, one database, until a domain earns its own host.
- Not an API-management product: a plain reverse proxy is enough while the only clients are TSR's.
- No business rules in the app or the site, and no domain layer on the device.
- Not Unity: Flutter reaches every device; an immersive XR experience would be a separate host.

### 2. Inside a domain

#### 2.1 Layers

DDD's layers exist thinly, inside each slice, not as folders across the codebase.

```
Flutter app ──HTTP──► endpoint ──► handler ──► domain ◄── infrastructure
(presentation         (presentation (application) (rules)   (DB, FCM, WhatsApp, Firebase)
 for people)           for programs)
                      └──────── domains/<context>/api/ ────────┘   composed by hosts/api
```

| Layer | What it does | Where |
|---|---|---|
| Domain | Rules and invariants, value objects, domain events. Depends on nothing | `domains/<context>/api/domain/` |
| Application | One use case: load, call the domain, save, publish through the outbox; owns the transaction; calls access's `can()` | the slice's handler, `domains/<context>/api/features/<slice>/` |
| Presentation (API) | HTTP endpoint: parse the request, call the handler, shape the response per the contract | the slice's endpoint, same folder |
| Infrastructure | Implements the ports at external boundaries: the database, FCM, WhatsApp, Firebase, clock | data access in the slice; plumbing in `shared/api/`; the Firebase verifier in `domains/identity/api/` |
| Composition | Wires the layers together (startup, DI, middleware order) | `hosts/api/` |

A slice does its own data access, without a repository interface. Interfaces exist only at
external services, per `CODING-GUIDELINES.md`. How it reaches the database is chosen per domain
(`dotnet-stack.md`): EF Core in the main JIT host, or Npgsql with hand-written mapping for a domain
that must run in an AOT host. At most those two patterns.

**AuthN, AuthZ and domain rules are three different places.**

| Concern | Owner |
|---|---|
| Who is calling: token verification, uid → member, sign-in, the account and its deletion | `identity` (AuthN), wired as middleware by `hosts/api` |
| What they may do and in which scope: roles, permissions, grants, scopes (gender, city, level), class-coordinator rules, the `class_access` rules view, `can()`, `GET /me/permissions` | `access` (AuthZ): a real domain with its own use cases (grant, revoke, assign, list) and data |
| Rules about a domain's own things: the teacher gender rule (gents may teach ladies' classes, not the reverse), "a class must be active" | the owning domain (`classes`), applied after `access` gives the scope |

- **`can()` is `access`'s public interface** (`domains/access/api/Permissions.cs`), not a slice
  and not a guard in `shared/`. Every handler calls it, so
  `access` is the one dependency every domain lists. The database, not a token claim, decides
  authority.
- **Gender segregation splits cleanly:** which gender a member may see is a scope in `access`;
  each domain applies that scope to its own data.
- **Today `PermissionsModel::can()` mixes all three** (scopes, the teacher gender rule, "a class
  must be active"). The class rules move to `classes` when `PermissionsModel` is rebuilt as slices
  move; until then the PHP model stays as it is, written once (`CLAUDE.md`).
- Identity owns the `users` table and account lifecycle; membership owns profiles and
  registrations; access owns the role, permission and grant tables.

#### 2.2 The app side

Flutter is presentation. Inside it, follow Flutter's official architecture guide (checked online
2026-11-08), whose layer names are Flutter's, not DDD's:

| Flutter layer | Holds | In `domains/<context>/app/` |
|---|---|---|
| UI | Views (widgets) and one view model per view: screen logic only (loading state, form state, what is enabled) | yes |
| Data | Repositories and services: calls to that domain's API through `shared/app`'s HTTP client | yes |
| Domain (optional) | Use cases for complex logic on the device | **no: skipped** |

TSR skips Flutter's optional domain layer: the domain lives on the server. Permissions, gender
segregation and class lifecycle are never re-implemented on the device. Form checks may run on the
device for a quick response; the API always checks again.

The repo root is the pub workspace root (Dart 3.6 and later; the app is on `^3.8.1`), because pub
finds members below the root. `hosts/app`, `domains/*/app` and `shared/app` are members.
`hosts/app` keeps the platform folders and is where Codemagic builds (`working_directory:
hosts/app`, one edit per workflow). Spiked 2026-11-08 in the sample: `flutter pub get` at the root,
a debug APK and an iOS `--no-codesign` build all worked. A signed store build through Codemagic is
not tried yet.

**The site side.** The public site is presentation too, built once per deploy instead of at
runtime. A domain with public pages adds `site/`: Razor components that render what its public
API returns, and one `<Context>Site.PagesAsync` that asks the API and says which pages exist. No
rule lives there: what is public is decided by the domain's query (a public read, rule 4 in
`domains/CLAUDE.md`), so the site cannot show a draft by mistake. Composition is `hosts/site`
(section 3.1). Proven by the site spike (2026-11-10) with `content` and `platform`.

#### 2.3 The spec: a domain defined once, implemented once at a time

A domain is defined once, language-neutral, in `domains/<context>/spec/`. Its rules are code, in
one implementation at a time. In DDD the domain model is code; infrastructure means the adapters
around it (database, queue, FCM), not language versions of it.

| Defined once in `spec/` | Format | Used for |
|---|---|---|
| Ubiquitous language: what a User, Member or Class is | `glossary.md` | names in every language |
| Actions: commands and queries | `api.yaml` (OpenAPI) | the published HTTP contract; whether it is generated from the C# endpoints or hand-written and checked is open (spike-learnings D2) |
| Events (`UserRegistered`, `UserDeleted` ...) | a table in the domain's `CLAUDE.md` for now; `events.yaml` (AsyncAPI) once a relay and a consumer exist (spike-learnings D1) | the shape producers and consumers agree on |
| Field shapes | inside `api.yaml` (`components/schemas`); a separate `schemas/` only when a second consumer needs them; tables stay in `db/migrations` | the HTTP contract |
| Behaviour and invariants | `tests/`: contract tests runnable against any base URL (target: Hurl files, `dotnet-stack.md`; the sample's are C#) | proving any implementation obeys the rules |

- **Rules are proven by contract tests.** Rules (invariants such as erasure or the gender scope)
  cannot be generated; the contract tests prove that an implementation obeys them. Types are not
  generated today: no generator exists, and each client (the Flutter repository, a `site/` module)
  copies the shapes it reads. Generating or checking them waits on D2.
- **One implementation per domain at a time.** During the move, `legacy/php` and the new API
  both implement a domain's spec and pass the same contract tests, then PHP's version is deleted.
  Long term, one implementation per domain, in whichever language that domain earns. Keeping the
  same rules in several languages would drift, and drift is where leaks come from.
- **A consumer is not a second implementation.** A Go worker that reacts to `notifications`
  events uses the domain's published events; it does not re-implement the domain.
- **The spec is the published language,** the shape clients see, not the domain model itself.

Which route source wins while slices move:
- **Until a path moves, the PHP route table stays the authority.** `web/api-docs.json` keeps being
  generated from it and gated in CI, unchanged (`docs/dev/api-contract.md`).
- **When a path moves,** its definition moves to the owning domain's `spec/api.yaml` in the same
  PR, and the gateway table sends it to the new API.
- **`tools/api-contract` fails the build** if a path appears in both the PHP table and a domain
  spec, or if the gateway table routes a path that neither defines.

Today's 191 paths carry operation tags partly by domain (`classes` 43 operations, `mcq` 18),
partly by audience (`admin` 51, `me` 17) and partly by mechanism (`reports` 37, `health`). They are
regrouped by domain as slices move.

#### 2.4 Rules

1. **A slice never calls another slice.** Shared rules move to the domain's `domain/` only once
   two slices need them. Until then, duplication between slices is fine.
2. **Domains talk through events first** (the outbox and Redis Streams already decided), never by
   writing or reading each other's tables directly. A direct call to another domain's public
   interface becomes a network call once the domains run apart, so such calls are rare and listed
   in the calling domain's `<Context>Module.Dependencies`.
3. **Commands write only their own domain's tables.** Queries may read across domains through read
   models (views, Elasticsearch, report tables). A cross-domain view is a read model owned by the
   domain that reads it, and is listed as a dependency like a direct call.
4. **`shared/` holds technical plumbing only, never a rule.** If only two domains need something,
   it is not shared.
5. **Interfaces only at external boundaries** (database, clock, FCM, WhatsApp, Firebase). No
   repository or service layer "just in case".
6. **Permissions and gender segregation are checked in the slice's handler**, through access's
   permission check. Never in the app, never in the gateway. The one exception is a public read
   (no sign-in): it has no caller to check, so its query returns only public data
   (`domains/CLAUDE.md` rule 4).
7. **The change test:** a typical business change touches one domain folder. If it keeps touching
   two, the boundary is wrong.
8. **A cross-domain report is owned by the domain whose question it answers** (e.g. the MIS report
   by classes), reads through read models only, and lists the domains it reads.
9. **Each domain module starts with only its listed dependencies** (access, plus any listed
   calls or views). The boundary test starts each module that way.
10. **Account deletion is one command in identity** that every owning domain must handle through
    an erasure event, delivered through the outbox; a test checks that every domain owning
    member data handles it (the privacy policy promises erasure).

What enforces them today: `hosts/api/tests` checks rules 2 and 9 for API modules (a module
references only `shared` and its listed dependencies, and starts with only those), and
`hosts/site/tests` does the same for `site/` modules. Both see real use of another module, not an
unused project reference. Flutter package imports are checked by Dart's own dependency lint. Rules
1, 3-8 and 10 are review-only; rule 10 has no test yet.

#### 2.5 Search: a read model fed by the event stream

`domains/search` owns no rules, only indexes. It consumes events from every domain (Stage 1 already
makes the search indexer the first consumer of the stream) and writes only its own Elasticsearch
indexes, so the owning domains do not know it exists (rules 2 and 3). One search box covers
classes, members and content.

1. **Permissions and gender segregation at query time.** Every indexed document carries its
   visibility fields (gender, city, level, class access). Every member query goes through
   access's `can()` and scopes and filters on them, as `SearchSourceModel` does in PHP today. A
   test per role proves a ladies' class never reaches a gents admin, and the reverse.
2. **Public and member search are physically separate.** Site search is unauthenticated, so it
   reads a public index that holds only published content and no member data. A filter bug there
   cannot leak a member.
3. **Rebuild without event sourcing.** Streams are trimmed and there is no event store, so the
   nightly rebuild (today's backstop) cannot replay history. Each source domain exposes one bulk
   "export for index" query, listed as a read model, and the indexer rebuilds from those.
4. **Events carry what search needs.** Prefer events that hold the indexed fields, so the indexer
   does not call back into the domains; otherwise it reads the export query.

Whether site search uses this API, a client-side index built at site build time, or both, is
still open (target architecture, open decision 5). The `public-search` slice serves the API option.

### 3. Around the domains

#### 3.1 `hosts/`: what runs or ships

- **`hosts/api`:** the one API process. It loads every domain's API module and wires middleware in
  order (identity's verifier first). It holds no rules, and runs the module-boundary tests.
- **`hosts/gateway`:** the reverse proxy for `api.`, introduced at Stage 2 to route the first
  slice.

  ```
  app / site / site search ──► api. ──► hosts/gateway ──┬─► legacy/php   (default: every path)
                                                         └─► hosts/api    (slices moved so far)
  ```

  - A small nginx container with its route table in the repo. Moving a slice is a
    one-line change, reviewed in a PR, and checked against the specs (section 2.3).
  - The local compose runs the same gateway, so contributors get prod's routing. Routes set in
    Dokploy's own Traefik would live in its UI, unreviewed and not reproducible.
  - Traefik stays the outer layer: it terminates TLS and sends `api.` to the gateway. One Dokploy
    change, agreed first.
  - It only forwards. Contracts, Firebase verification and permissions stay in the API.
  - Not an APIM (Azure API Management, Kong, Tyk): keys, per-client rate limits, a developer
    portal and usage analytics are for third-party consumers. Reconsider if outsiders call the
    API.
  - **Store-live safety:** it is a single point of failure for every installed build. It is
    stateless, with a healthcheck that uses a tool the base image has (Alpine: BusyBox `wget`, no
    `curl`). `api.` goes through it first; `mobile-api.` moves behind it only after it has served
    `api.` cleanly for one release. Rollback is one Traefik line back to `mobileapi`. The
    `mobile-api.` alias stays until `minimumBuild` passes the first build that calls `api.`.
- **`hosts/scheduler`:** one process that calls the same command handlers, replacing cron and the
  `web/cli` jobs as their handlers move; it also runs the outbox relay (Stage 1+). Until then,
  cron and `web/cli/*` stay in `legacy/php`. Where it runs in production is open (target
  architecture, open decision 4).
- **`hosts/app`:** the Flutter shell, with the platform folders, built by Codemagic. Today's
  `lib/features/` groups by screen area (`admin`, `reports`, `wordpress`, `grand_quiz` ...), not by
  domain. Screens move into domain packages as they are touched, not in one go.

  It is the one client for every device: Flutter targets phones, tablets, desktop and web, and XR
  devices (Android XR, Vision Pro, Meta Quest) run it as a flat window (checked online
  2026-11-08). On Quest, push and Google sign-in probably will not work (no Google Play
  Services; not tested). An immersive XR experience would be a separate host (`hosts/xr/`, Unity)
  on the same API; Unity is not the main client because its web builds are not indexable and
  Arabic and Urdu right-to-left text needs a plugin.
- **`hosts/site`** (decided 2026-11-10, `docs/specs/site-spike/results.md`): a .NET console program
  that renders Razor components to plain HTML with `HtmlRenderer`, no JavaScript. Each domain that
  has public pages adds `domains/<context>/site/` (a Razor class library); `hosts/site/SiteModules.cs`
  lists them, like `hosts/api/Modules.cs`, and `hosts/site/tests` checks that each references only
  `shared/site` and builds its pages alone. A site module reads the API, never the database, and
  copies the response shapes it needs from `api.yaml`. The host owns the layout, the home page and
  the navigation; any API error stops the build. tsr-web's Next.js pages are rewritten, not moved.
  The client-side search index (section 2.5) is not built yet.
- **`hosts/calendar`:** a program with its own logic, not a thin host: the calendar feed has its own
  date logic (`ics_feed.py`, `hijri.py`) and reads private inputs. They hold no member or class
  rules. Whether tsr-web's Elasticsearch is the same one as the API's is not verified.
- **`hosts/media`:** the CDN config for `media.`.

#### 3.2 Deploying and scaling a domain on its own

A host chooses which domain modules it loads. Today `hosts/api` loads all of them: one process on
one Dokploy server is the cheapest to run and debug at TSR's size. When a domain needs its own
deploy or scaling (for example assessment during a Grand Quiz), a new host folder loads that
module alone, and the gateway sends its paths there. No code moves; it is a production change,
agreed first.

- Workers already run apart: the notifier is its own container, and the search indexer will be.
  Search queries can get their own host too, so search load never slows the core API.
- The app does not split: the stores ship one binary. On the web, deferred loading can fetch a
  domain's screens on demand; that is lazy loading, not separate deployment.
- The database stays shared and is the real limit on scaling. Table ownership keeps a later split
  possible, but a domain with its own database is a much bigger step, only under real pressure.
  Cross-domain views (rule 3) would have to become events first.
- What keeps it cheap: rules 2, 3 and 9 (events first, listed dependencies, each module starts
  with only those).

#### 3.3 `shared/`, `db/` and `legacy/`

- **`shared/`:** `shared/api` (db access, clock, outbox writer, request context, the call
  signature of access's `can()`), `shared/app` (design system, HTTP client, auth session
  plumbing) and `shared/site` (the page description and the build-time API reader). No rules.
- **`db/`:** one database; ownership is per table. **Platform-owned tables** belong to no domain:
  `outbound_messages` and the outbox, `schema_migrations`, `admin_access_log`.
  - **Target (`dotnet-stack.md`):** PostgreSQL with one schema and one DbContext per domain, and
    **EF migrations** holding all schema and base data (permissions catalog, role grants, lookups,
    synthetic dev data) in this public repo, deployed as a migration bundle before the app starts.
    The private repo keeps member data and prod config only. **Open:** whether each domain's
    migrations live with its DbContext in `domains/<context>/api/` or together in `db/migrations`.
  - **Until the move:** MariaDB, and tsr-migrate (Go, in tsr-account) applies one ordered directory
    keyed by file name and checksum. tsr-migrate does not come to tsr-app. The sample's
    `db/migrations/*.sql` and `db/dev-init/load.sh` stand in for it locally.
  - **Moving today's `migrations/` to `db/migrations`** (only if the MariaDB history moves at all
    before Postgres) is not a plain rename. The lint compares against
    the base tree, so from the new path all 67 files look added and the legacy `001_*` and
    `*_rollback.sql` names fail. It needs a one-off lint exemption, and three production files
    hardcode the old path: `.docker/entrypoint.sh:21`, `.docker/Dockerfile.webapp:84` and
    `.github/workflows/migrations-lint.yml:26,32`. It lands with the deploy-source switch.
- **`legacy/php/`:** not restructured. Its `web/models/` (43 files) map onto the domains in
  section 4; which model moves first is decided per slice.

#### 3.4 `tools/`, `.claude/` and `docs/`

- **`tools/`:** the contract builder, auth emulator, perf, geonames, `scripts/` (including the
  gate's `check-real-data.sh`), security scanners and baselines, and `tools/ai/` for runnable AI
  dev tooling (orchestrators with an API key scoped per run, MCP servers and CLIs that agents call,
  evals).
- **`.claude/`:** agent and skill definitions, where Claude Code discovers them. A skill about one
  domain lives in `domains/<context>/.claude/skills/` and shows up only when working there. No
  symlinks between `.claude/` and `tools/ai/`, because they break on Windows.
  - AI dev tooling is public like the code it works on. Domain-first suits agents: one domain is
    one folder of context.
  - Personal agents (`pa`, `personal`, `whatsapp`, in Asif's own `asifshakir/agents`) stay in that
    repo. Its `install.sh` can install the TSR agents from tsr-app.
  - Each `agent.md` and skill is read for quoted data (names, tokens, hostnames, figures) before
    it enters the public repo. `infra` mixes Imantix and TSR server detail; its prod-specific
    parts stay private, which may mean it stays out.
  - AI inside the product (e.g. `domains/search/embeddings/`) is product code, not tooling.
- **`docs/`:** `docs/dev/` (how-to per area, the `CLAUDE.md` router target), `docs/templates/`
  (the capability template) and `docs/specs/` (research and spikes only, not feature work).
  - **Documentation model (2026-11-10):** the lasting record of a feature is its **living capability
    document** in `domains/<context>/capabilities/`, rewritten by every PR that changes behaviour.
    The spec (GitHub issue) and plan (draft PR description, with its verification plan) are change
    documents and stay on GitHub. There is no `plan.md` or `tasks.md` in the repo.
  `AGENTS.md` at the root points other AI tools to `CLAUDE.md`.
- **Windows:** deeper paths (`domains/*/app/lib/features/...`) under Gradle are a long-path risk;
  not verified. The README tells Windows contributors to set `core.longpaths`.

### 5. Why this layout, and what it costs

Why:
- **A change is local.** A change to classes touches `domains/classes/` only: its API slice, its
  screen and its spec, reviewed together. An agent or a contributor needs one folder of
  context.
- **Moving off PHP is slice by slice.** The gateway routes one path, which is one slice.
- **A domain can deploy and scale on its own** with a host and a gateway line, and clients do not
  notice (section 3.2). Nothing forces that now.
- **Adding a use case is adding a folder**, not editing layers across the codebase.

Costs:
- The Flutter app is split into workspace packages, once and gradually, after the spike.
- `hosts/api` and `hosts/app` rebuild when any domain changes: their watch paths are their own
  folder plus `domains/**` and `shared/**`.
- Build files multiply: each domain carries one per stack it has (`api/`, `app/`, `site/`), plus
  test projects.
- Moving today's folders needs production changes (section 3.3 and "When this layout applies").
